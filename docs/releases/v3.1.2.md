## Summary

v3.1.2 is a hardening patch. It closes the last unguarded mutating UI route, fixes a
teardown race between deferred evaluation and the database, and carries the image,
dependency and CI fixes that were merged after v3.1.0. There are no HTTP API route
changes, no CLI command changes and no database migrations.

It also repairs the release workflow itself. The v3.1.1 tag was pushed, but the
tag-triggered run failed in `preflight` and published nothing: no GitHub Release, no
release assets and no container images. The cause was a guard that asked the
checkout-owned `refs/tags/<tag>` ref what type it was, after `actions/checkout@v5`
had already rewritten that ref to the peeled commit. That guard is replaced here,
and the payload v3.1.1 intended to ship is what v3.1.2 publishes.

## Security

### Every mutating UI route now enforces CSRF

`POST /ui/api/analysis` was the last mutating `/ui/api/*` route that depended on
`require_session` instead of `require_csrf`. Since `require_csrf` performs the
session check itself, the route kept its authentication while the missing CSRF guard
was closed. `SameSite=Lax` does not stop a top-level form POST, so this was the one
remaining cross-site write path in the native UI.

The test guards are dynamic rather than a hard-coded list: the suite walks the live
router and asserts that all eleven mutating `/ui/api/*` routes declare
`require_csrf`, that a token-less request is refused with the dependency's own
`403 FORBIDDEN` message, and that the same request with a valid token is no longer
refused by that layer. A route-count guard and a static declaration check make a
forgotten dependency fail closed, and the previous exemption list is gone.

### Dependency advisories

Pillow is pinned to `13.0.0` exactly (not a floor) in every installable surface:
`pyproject.toml`, `requirements.txt`, `requirements.lock` and the runtime/gpu
groups. Pillow 12.3.0 carries one CRITICAL and six HIGH advisories whose fix version
is 13.0.0, and `pip-audit --strict` plus the image scans both block on them. The
exact pin is what makes the worker image converge: it installs the torch stack first,
and `torchvision` declares an unbounded `pillow>=5.3.0` that a floor would leave
satisfied at whatever version the index served.

Gradio was removed from the published dependency graph: it requires `pillow<13` and
therefore made the 13.0.0 pin uninstallable. The web UI is the native FastAPI page
(`src/fiximg/ui/web/`), and no published install path resolves Gradio any more.

### filelock raised to 4.2.1

The first pull-request CI run for this release failed on the worker image scan, not on
code: Trivy reported `filelock` 3.32.3 with `CVE-2026-112940` (HIGH, arbitrary file
overwrite through the SQLite lock database). The image reaches 3.32.3 because it
installs the torch stack first, and `torch==2.7.1` requires `filelock` with no upper
bound, so the `3.20.3` pin in the requirement files never took effect there.

`filelock` is now required at `>=4.2.1` in `pyproject.toml` and pinned to `==4.2.1` in
`requirements.txt`, `requirements/runtime.txt` and `requirements/gpu.txt`. 4.2.1 is the
upstream fix version for the advisory and requires Python 3.11 or newer, which is
already the floor for this release. The only in-tree caller of the `filelock` API is
`config/security.py`, which has no importers; its `with FileLock(path)` usage is
unchanged in 4.2.1.

The image scan has not been re-run here: the next CI round on this branch is what
proves the worker image now scans clean.

## Reliability

### Deferred evaluation can no longer outlive its teardown

Evaluation of a completed task runs on a single-worker background pool so the result
stays downloadable before the metrics exist. A non-blocking shutdown used to drop the
only reference to that pool, which made the later blocking shutdown a no-op: an
in-flight evaluation could outlive worker/app teardown and write into the database a
test fixture had already repointed. On Python 3.12 CI this surfaced as
`no such table: users` in the *following* test's app startup.

The pool lifecycle now keeps every detached pool until it is drained, so a later
`wait=True` waits for all generations; submission and pool retirement share one lock,
so a job is either queued in a pool that the teardown drains or refused outright.

`PipelineWorker.stop()` was tightened at the same time:

* it closes deferred-evaluation admission *before* joining its thread, so a task that
  finishes on a thread which outlives `timeout` cannot schedule new evaluation work;
* it returns `True` only when the intake was closed, the thread exited and the drain
  succeeded, and logs `gpu worker stop incomplete` with the three booleans otherwise;
* a refused evaluation is logged as `async evaluation skipped` with its task id
  instead of disappearing silently.

Normal operation is unchanged: evaluation is still asynchronous and never blocks the
task result. Regression coverage lives in `tests/unit/test_eval_pool_lifecycle.py`
(thirteen deterministic tests, no sleep-driven races).

### Redis queue polls no longer time out before the reply

The Redis client's `socket_timeout` was equal to the blocking read it wrapped, so a
poll could time out before the reply arrived and no task was claimed. The timeout now
clears the blocking read with margin.

### Migration history prints on non-Unicode consoles

`fiximg-db history` echoes revision docstrings containing an em dash and a section
sign; on a console code page without those characters it aborted with
`UnicodeEncodeError`. It now degrades the unprintable characters and still prints the
history.

## Configuration and storage

### Invalid profiles fail fast

A profile file that exists but cannot be parsed, or one the deployment explicitly
requested but which is absent, now raises at startup instead of silently booting on
development defaults. Declaring `database_url` inside a profile is refused by name,
because a value read from there would outrank the `FIXIMG_DATABASE_URL` an operator
set. The shipped profiles declare none of the refused keys.

### Management paths follow the configured database

The API token file and the one-time administrator password file are written beside the
database the process actually opens, derived from the same resolved management-data
path, instead of next to the default database.

## Images and CI

* **Released CPython 3.11 in the worker and root images.** Their previous base shipped
  only a 3.11 release candidate, which does not satisfy the project's `>=3.11`
  requirement, so pip silently resolved older dependencies while the build reported
  success. Both now take the interpreter from the official `python:3.11` image and copy
  the CUDA userspace from the NVIDIA image.
* **Each image is validated in its own runner.** The three images do not fit one
  standard hosted runner; the job is a matrix (one shard per image: build, smoke,
  scan) with an explicit disk-budget check before each build, and a separate job
  validates the compose files once.
* **Runtime dependencies are asserted inside the built images.** The check reads
  `importlib.metadata` in the container (Pillow must be 13.0.0; Gradio distributions
  must be absent) and runs before the Trivy scan, so an install-order regression is
  reported as itself rather than as a scan finding.
* **CI declares least-privilege permissions.** `ci.yml` runs with
  `contents: read`; the release workflow keeps write access only in the jobs that
  actually publish (see the workflow itself).
* **Release workflow hardening.** Top-level permissions are read-only; registry and
  Release write access is scoped to the publishing jobs. A manual dispatch is always a
  dry run. A tag-triggered publish requires the tag to equal `v<pyproject version>`,
  to be an annotated tag, and to point at the exact commit of `origin/main` — all
  checked before any registry or Release write. Packages, both image preflights and
  the test matrix complete before any registry login; images are staged by digest and
  promoted only after both preflights succeed, with `latest` promoted after both
  version tags.
* **Release notes come from this file**, not from commit subjects, and the workflow
  appends the artifact checksums and image references.


### The release workflow proves the annotated tag without trusting the checkout

The v3.1.1 tag push failed in `preflight` before any Release, asset or image was
published. `actions/checkout@v5` checks a tag push out by fetching the tag object and
then force-updating the checkout-owned `refs/tags/<tag>` ref to the peeled commit, so
the guard's object-type test saw a lightweight ref and rejected a valid annotated tag.
The same assumption would also have titled the Release after the tag name instead of
using the tag annotation, and it would have done so silently.

`scripts/ci/release_tag_guard.sh` now owns that proof. It refuses any name that is not
`vMAJOR.MINOR.PATCH`, refuses an expected commit that is not a full lowercase SHA, and
fetches the remote tag into `refs/release-tags/<tag>` -- never into the checkout-owned
ref, never with a force refspec, and never over a private ref that already exists. It
then requires that private object to be a `tag` whose peeled commit equals both the
caller's expected commit and `origin/main`. The release title is read from the private
tag object, must be a single non-empty line, must contain no control character, and
must fit a 200-byte budget; the validated value reaches the `release` job through an
environment variable, so it is data and can never be shell text.

`tests/unit/test_release_tag_guard.py` reproduces the runner state with real git
repositories: it rewrites the public tag ref to the peeled commit and asserts that the
guard still resolves the annotation, and it covers lightweight tags, a tag on an older
commit, a missing tag, malformed and injection-shaped tag names, an invalid expected
SHA, an empty annotation, an over-long title, control characters, shell metacharacters
and a stale private ref.

## Upgrade notes

Upgrade in place. There are no database migrations, no HTTP route changes and no CLI
changes. Points worth checking:

1. **Your configuration must be valid.** A profile that never parsed strictly may now
   fail at startup where it previously booted with defaults; the error names the file
   and, for a parse failure, the position.
2. **Remove `database_url` from any profile file.** Set `FIXIMG_DATABASE_URL` in the
   environment instead.
3. **Generated secret files may move.** If you relocated the database, the API token and
   the one-time administrator password are now written beside *that* database. Move an
   existing token file or set `FIXIMG_API_TOKEN` explicitly.
4. **Rebuild images rather than reusing cached ones.** The interpreter base, CUDA
   userspace, queue client and Pillow pin all changed.
5. **UI behaviour is unchanged for users**, but a browser tab that cached the previous
   static assets should be reloaded once so the CSRF token flow is in effect.

No environment variable was removed and no default value changed.

## Known limitations

* **GPU inference is not covered by hosted CI.** Hosted runners have no GPU; CI proves
  the image is a CUDA build and that the CUDA libraries load, and real device inference
  is verified separately on a GPU host.
* **The worker and root images are large** (roughly 17–18 GB each). They fit one runner
  per image after the toolchain reclaim, and the build is the slowest part of CI.
* **The eval pool is process-wide.** In a single process running more than one worker or
  app, one worker's stop drains the process-wide evaluation pool. Current deployments run
  one worker per process, and the admission gate itself is per orchestrator.
* **A worker thread that outlives `stop(timeout)` may still write task rows.** The fix
  guarantees that no *new deferred evaluation* is produced and that accepted evaluation
  is drained; a thread stuck in long inference can still complete its own task row.
* **Python 3.11/3.12 runtime verification happens in CI.** The local verification for
  this release ran on a newer interpreter; the 3.11/3.12 matrix is the gate.
* **Face detection models are distributed separately.** The images ship code only; the
  dlib landmark model is restricted to research and non-commercial use.
